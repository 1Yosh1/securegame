# SecureGame Class, Method, and OOP Report

## 1. Scope and reading guide

This report catalogs the first-party SecureGame application source and its checked-in tests as they exist in this workspace. It covers **59 production Java source files**, **17 Java test source files**, the three maintained browser scripts in `src/main/resources/static/`, and the two root-level test/support scripts. Java nested classes, interfaces, records, and enums are included. Generated Vaadin/framework assets under `src/main/frontend/generated/`, dependencies, build output, and repository-agent tooling under `.claude/` are not SecureGame application classes and are not catalogued as authored product code. The static-site JavaScript has no `class` declarations; its functions and object-literal methods are described as such, not mislabeled as JavaScript classes.

For each source-declared Java method and constructor, the entries explain its responsibility and the main execution steps. Record component accessors, `equals`, `hashCode`, `toString`, and compiler-supplied default constructors are generated by Java rather than written as method bodies; they are identified separately and not presented as hand-written methods. Repository query methods are declared in the project, but their database implementations are generated by Spring Data at runtime.

> **Source accuracy note:** Some comments describe behavior more broadly than the implementation. For example, `AnomalyFusionEngine` calculates a normalized weighted average (not a vote), and `SimulationEngine` performs synchronous policy checks and logging (it does not implement the priority event queue mentioned in its class comment). The report follows executable source.

## 2. Application architecture at a glance

The Spring Boot application starts from `SecureGameApplication`. REST and STOMP controllers translate browser requests/messages into service calls. Services and engines compose repositories and domain logic. JPA model classes hold persisted data. The anomaly and risk subsystems are deliberately separated into input/value types, scoring strategies, fusion/orchestration, and report values. The browser UI is implemented with ordinary JavaScript functions plus `GameRegistry` and `MiniGames` object literals.

The central flows are:

1. **Anomaly evaluation:** `GameController` builds a `SessionContext`; five `AnomalySignal` implementations score it; `AnomalyFusionEngine` computes one weighted-average score and returns `AnomalyReport`.
2. **Session risk:** `RiskController` builds a `RiskFeature`; `RiskEngine` combines `RuleBasedLayer` and `LogisticRegressionModel`, ranks rule contributions, and asks `CoachFeedbackGenerator` for tips.
3. **Simulated login:** `SimulationController` calls `SimulationEngine`; the engine checks lockout, password entropy, and scenario MFA policy and writes `EventLog` records.
4. **Authentication:** `AuthController` validates input, hashes passwords, handles OTP/device tokens, and delegates email and user persistence to `EmailService` and `UserRepository`.
5. **Play:** `game.js` manages UI/session state; `GameRegistry` dispatches topics; `MiniGames` owns the interactive mini-game implementations; `campaign.js` supplies campaign-level data.

## 3. OOP concepts present in the actual code

### Encapsulation

Encapsulation bundles state with the operations that expose or change it, and controls access to that state.

- JPA entities such as `UserEntity`, `Scenario`, `PlayerProfile`, and `LeaderboardEntry` keep fields `private`; callers use getters/setters rather than directly accessing fields. Their public setters mean these entities are mutable, so their encapsulation is access-controlled rather than immutable.
- `AuthController.OtpChallenge` is a stronger example: the nested class is `private static final`, its salt, digest, and expiry fields are private and final, and only private accessors are provided. Its attempt count is private mutable state, updated by the enclosing authentication flow. Code outside `AuthController` cannot create or inspect challenges.
- `AuthController` owns the OTP and device-token maps and exposes operations such as `consumeOtp`, `isValidDeviceToken`, and endpoint methods rather than the maps themselves. The maps are private implementation details.
- `PlayerProfileController.PlayerView` is a boundary projection: it exposes ordinary player fields but deliberately does not include `totpSecret`. `PlayerProfile.totpSecret` also has `@JsonIgnore`. This limits accidental disclosure at the HTTP/JSON boundary.
- `EventLog` exposes getters and constructors but no setters in the actual source. It is therefore effectively append-only through ordinary application code, even though its source comment inaccurately mentions a setter for `details`.

### Abstraction

Abstraction gives callers a stable contract while hiding the implementation details behind it.

- `AnomalySignal` defines the contract `score(SessionContext)`, `name()`, and `weight()`. The fusion engine does not need to know each algorithm’s internal math.
- Spring Data repository interfaces such as `UserRepository` extend `JpaRepository` and declare domain queries. Application services depend on those contracts; Spring Data supplies proxy implementations and generates query behavior from method names.
- Controllers hide HTTP input/output mechanics from services. For example, `SimulationController` accepts a request and maps a `LoginResult` to a response map, while `SimulationEngine` owns the policy decisions.
- `TOTPService` wraps the third-party TOTP generator/verifier behind `generateSecret()` and `verifyCode()`. Callers need not manipulate the library’s generator or clock classes.

### Inheritance and interface realization

There is very little application class-to-class inheritance, and that distinction matters.

- All eight repository interfaces **extend** Spring Data’s `JpaRepository<entity, Long>`. This is interface inheritance: they receive the repository contract, including standard CRUD operations, and add project-specific query declarations.
- `WebSocketConfig` **implements** Spring’s `WebSocketMessageBrokerConfigurer`; its two `@Override` methods customize the framework extension points. This is interface realization, not subclassing a project class.
- The signal strategy classes implement `AnomalySignal`. That creates substitutability and is most directly useful as polymorphism; it is not class inheritance. The fusion engine receives `List<AnomalySignal>` through constructor injection, so adding a Spring-managed strategy does not require changing its constructor.
- No production class in the inventoried application source extends another project-defined concrete class. Ordinary `Object` ancestry is implicit Java behavior and is not used as a design example here. Annotations, constructor injection, and composition are not inheritance.

### Polymorphism

Polymorphism lets code invoke one contract while the actual implementation varies by runtime object.

- `AnomalyFusionEngine.signals` is an injected `List<AnomalySignal>` containing the signal strategy beans, such as `TimeOfDaySignal`, `GeoDistanceSignal`, `UserAgentSignal`, `FailedAttemptSignal`, and `DeviceTrustSignal`. Its loop calls `score`, `name`, and `weight` through the interface; Java dispatches each call to the concrete signal implementation.
- Spring injects that collection into the engine constructor. An additional strategy bean can participate by implementing the contract, without expanding a constructor signature that enumerates every implementation.
- The repository interfaces are implemented at runtime by Spring Data proxies; services invoke repository methods through interfaces without depending on a handwritten concrete repository class.
- `GameRegistry` provides a JavaScript analogue of strategy/dispatch: a topic key resolves to a function with a common `(difficulty, onWin, onLose)` calling shape. It is function dispatch, not class-based Java polymorphism.

### Composition and dependency injection

Composition is the clearest overall structural pattern. `RiskEngine` holds a `RuleBasedLayer`, a `LogisticRegressionModel`, and a `CoachFeedbackGenerator`; `SimulationEngine` holds repositories and a `TOTPService`; controllers hold the service/repository collaborators they need. Constructors receive those collaborators, which makes dependencies explicit and lets Spring manage application instances. This is composition, not inheritance.

### Records and value-oriented modeling

Records such as `RiskFeature`, `SessionContext`, `RiskAssessment`, and request/response DTOs package related data into concise types. They automatically receive component accessors and value-oriented methods from the compiler. Records are shallowly immutable: component references cannot be reassigned through generated setters (there are none), but a referenced array or collection may itself still be mutable. The code’s record components therefore provide a compact data shape, not a guarantee that every referenced object is deeply immutable.

## 4. Production Java catalog

### 4.1 Application bootstrap and startup data

#### `SecureGameApplication` — `src/main/java/com/unime/securegame/SecureGameApplication.java`

- `main(String[] args)`: JVM entry point. Passes the application class and command-line arguments to `SpringApplication.run`, which starts Spring Boot, scans/configures components, and launches the server.

#### `DataSeeder` — `src/main/java/com/unime/securegame/DataSeeder.java`

- `seedData(ModelWeightRepository, CoachFeedbackRepository, SyntheticDataGenerator, LogisticRegressionModel)`: Spring `@Bean` factory that returns a `CommandLineRunner`; the runner executes after application startup. If there are no model weights, it saves six defaults, creates 3,000 deterministic synthetic examples (seed 42), trains the logistic model for 300 epochs at learning rate 0.1, then stores `riskVectorVersion`. For an existing legacy database without that marker, it flips the legacy password-entropy coefficient and adjusts bias to preserve predictions under the changed risk-vector direction, then stores the marker. Independently, if coach feedback is empty, it saves the curated feedback rows. It exists to bootstrap first-run scoring and supply feedback without manually populating the database.

### 4.2 Anomaly subsystem

#### `AnomalySignal` — `anomaly/AnomalySignal.java` (interface)

- `score(SessionContext)`: contract for producing a normalized anomaly value, where 0 means ordinary and 1 means maximally anomalous. Each implementation applies its own input-specific calculation.
- `name()`: contract for a stable human-readable key used in the report breakdown and reason.
- `weight()`: contract for the signal’s fusion weight. `AnomalyFusionEngine` multiplies this by the score; implementation weights sum to 1.0 in the current set.

#### `SessionContext` — `anomaly/SessionContext.java` (record)

Carries player/scenario identifiers; current and known latitude/longitude; current and historical login hours; current and known user-agent strings; failure streak; device-trust score; and session time. Its canonical constructor and component accessors are compiler-generated.

- Convenience constructor (12 arguments, ending in `failStreak`): delegates to the canonical constructor, supplying device trust `1.0` and `Instant.now()`. It keeps simple callers/tests from having to specify those default values.

#### `AnomalyFusionEngine` — `anomaly/AnomalyFusionEngine.java`

- Constructor: accepts the five signal beans in fixed order and stores them with `List.of`. It creates a uniform collection to process rather than embedding individual signal math in the engine.
- `evaluate(SessionContext)`: loops through signals; records each named score; accumulates score×weight and total weight; divides to get a normalized weighted average (or zero if total weight is zero); clamps to `[0,1]`; maps the result to an alert level; derives an explanation; and returns an `AnomalyReport` containing score, level, breakdown, reason, player, and scenario.
- `toAlertLevel(double)`: maps `<.25` to `CLEAR`, `<.50` to `WATCHLIST`, `<.75` to `CHALLENGE`, and the rest to `BLOCK`. The thresholds centralize severity policy.
- `buildReason(Map, AlertLevel)`: returns a fixed normal-session message for `CLEAR`; for other levels, finds the top-scoring signal and inserts it into a monitoring, step-up, or block explanation.
- `topSignalName(Map)`: selects the map entry with greatest score and returns its key; falls back to `"unknown"` for an empty map.

Nested types:
- `AlertLevel` enum: `CLEAR`, `WATCHLIST`, `CHALLENGE`, and `BLOCK` are the finite states used by reports and policy thresholds.
- `AnomalyReport` record: holds the output data; its accessors are generated. `requiresAction()` returns true only for `CHALLENGE` and `BLOCK`, giving callers a simple policy predicate.

#### Concrete signal implementations — `anomaly/signal/`

All implement `score`, `name`, and `weight`; their three methods satisfy the common `AnomalySignal` contract and support uniform fusion.

- `DeviceTrustSignal`: `score` inverts `deviceTrustScore` (`1 - trust`) and clamps it to `[0,1]`; `name` returns `deviceTrust`; `weight` returns `.15`. It makes unfamiliar/untrusted devices contribute positively to anomaly risk.
- `FailedAttemptSignal`: `score` returns 1 at a streak of at least five, otherwise the streak divided by five and capped at 1; `name` returns `failedAttempts`; `weight` returns `.15`. The hard threshold makes repeated failure fully suspicious.
- `GeoDistanceSignal`: `score` calls `haversine` on known/current coordinates, returns 1 above 2,000 km, otherwise clamps `(distance - 50) / 500`. `haversine(double lat1, double lon1, double lat2, double lon2)` converts coordinate deltas to radians and applies the great-circle Haversine formula using a 6,371 km Earth radius. `name` returns `geoDistance`; `weight` returns `.30`, the largest current signal weight. The helper is public and independently testable.
- `TimeOfDaySignal`: `score` computes `abs(currentHour - avgLoginHour) / max(stdLoginHour,1)`, divides by the 3-sigma threshold, and caps at 1. `name` returns `timeOfDay`; `weight` returns `.20`. A minimum deviation denominator avoids division by zero.
- `UserAgentSignal`: `score` returns `.5` when either string is absent, 0 for exact equality, otherwise `1 - jaroWinkler` clamped to `[0,1]`. `jaroWinkler(String,String)` returns exact equality as 1; otherwise it computes Jaro similarity and adds the common-prefix boost (up to four characters, factor `.1`). Private `jaro(String,String)` finds matching characters within a match window, counts transpositions among matched characters, and evaluates the Jaro formula; empty or unmatched inputs return 0. `name` returns `userAgentMismatch`; `weight` returns `.20`.

### 4.3 WebSocket configuration

#### `WebSocketConfig` — `config/WebSocketConfig.java`

Implements `WebSocketMessageBrokerConfigurer`.
- `registerStompEndpoints(StompEndpointRegistry)`: registers `/ws` and enables SockJS fallback for browsers without native WebSocket support.
- `configureClientInboundChannel(ChannelRegistration)`: installs `ClassroomChannelInterceptor` to reject unauthenticated/unauthorized subscriptions and unsupported inbound destinations.
- `configureMessageBroker(MessageBrokerRegistry)`: enables the in-process `/queue` and `/topic` broker destinations and sets `/app` as the client-to-server prefix. Classroom topic changes are delivered through per-user `/queue` subscriptions after room-membership checks.

`SecurityConfig.securityContextRepository()` supplies the same HTTP-session repository to Spring Security and `AuthController`, allowing OTP/device-token login to persist authenticated sessions. `AdminApiKeyFilter` intentionally assigns API-key roles only to the current request and does not save that authority to a session.

### 4.4 Controllers and HTTP/STOMP boundary types

Controllers convert request data into calls to services/repositories and convert results into HTTP response shapes. They should not be confused with the underlying scoring or persistence algorithms.

#### `AuthController` — `controller/AuthController.java`

Dependencies are constructor-injected `EmailService`, `UserRepository`, and `ClassroomRepository`; a two-dependency convenience constructor remains for direct unit tests. OTP challenges and device tokens are held in private concurrent in-memory maps. The public endpoints are described below; helpers support those flows.

Private helpers:
- `generateToken()`: fills 32 bytes with `SecureRandom` and returns URL-safe, unpadded Base64 for a device token.
- `generateOtp()`: produces a zero-padded six-digit code using `SecureRandom` and `Locale.ROOT`.
- `normalizeEmail(String)`: maps null to empty, trims whitespace, and lowercases with a locale-independent locale so repository lookups use a stable key.
- `isValidEmail(String)`: requires non-null, at most 254 characters, and a basic non-whitespace `local@host.tld` shape.
- `storeOtp(Map,String,String)`: generates a 16-byte random salt, hashes code+salt through `otpDigest`, sets expiry to current time plus 300 seconds, stores the challenge under email, and returns the exact stored challenge (used to remove it if email fails).
- `otpDigest(String,byte[])`: SHA-256 hashes the salt followed by UTF-8 code bytes. A missing SHA-256 provider becomes `IllegalStateException`, not a successful authentication path.
- `consumeOtp(Map,String,String)`: uses `ConcurrentHashMap.compute` per email to expire/remove stale codes, increments attempt count, compares digests via constant-time `MessageDigest.isEqual`, removes successful codes, and removes codes after five failed attempts. Returns whether the submitted code was valid.
- `isValidDeviceToken(String,String)`: obtains the issued token, rejects missing/expired entries (removing expired values), and constant-time compares UTF-8 token bytes. This prevents ordinary string equality timing behavior.
- `hashPassword(String)`: generates a fresh 16-byte salt, derives a 256-bit PBKDF2-HMAC-SHA256 result for 600,000 iterations, and stores a self-describing `pbkdf2-sha256$iterations$salt$hash` string.
- `passwordMatches(String,String)`: rejects nulls; for PBKDF2 strings validates field count, iteration range (100,000–2,000,000), decoded salt/hash lengths, derives the supplied password with the stored salt/iterations, and compares in constant time. If the stored value is not in the PBKDF2 format, it checks the legacy Base64 SHA-256 representation so a successful legacy login can be upgraded.
- `derivePassword(String,byte[],int)`: uses `PBEKeySpec` and `PBKDF2WithHmacSHA256` for 256 bits; wraps unavailable crypto as `IllegalStateException` and clears the password in the spec in `finally`.
- `loginResponse(UserEntity,String)`: constructs the success map containing status, role, XP, level, and device token. Centralizes the shape shared by OTP and trusted-device login.

Nested types:
- `DeviceToken` record stores token value and expiry; its record accessors are generated.
- `OtpChallenge` is a private static class. Its constructor stores salt, digest, expiry; private `salt()`, `codeDigest()`, and `expiresAt()` accessors expose those parts only to the enclosing controller. Attempt count is updated by `consumeOtp`.

Endpoints:
- Constructor: stores the injected mail and user repository collaborators.
- `register(email,password,name,role,classroomCode)`: normalizes and validates email, 12–128-character password, and nonblank bounded name; rejects duplicates; hashes the password; deliberately ignores self-selected role/classroom and stores role `PENDING`, no classroom, level 1, XP 0; saves and returns success. The ignored request fields exist for legacy/request compatibility, not for privilege assignment.
- `updateRole(email,role,deviceToken)`: normalizes/validates email, requires the same authenticated identity and a valid trusted-device token; permits only `STUDENT` or `SOLO`; loads the user, changes and saves role, or returns the appropriate unauthorized/bad-request response.
- `login(email,password)`: validates input, fetches the user, checks password, migrates a verified legacy hash to PBKDF2, creates/stores a one-time OTP, then sends it. If sending fails it removes that exact OTP and returns 503; on success it returns `otp_sent` and role.
- `loginWithToken(email,password,deviceToken)`: repeats email/password verification and legacy-hash upgrade, then validates the device token; on success returns the common login response, otherwise reports invalid credentials or unauthorized device.
- `verifyOtp(email,otp)`: requires a valid email and six digits, consumes the one-use OTP, fetches the user, issues a 30-day device token, and returns `loginResponse`; invalid/expired OTPs return a generic invalid-OTP response.
- `logout(email,deviceToken)`: requires the same authenticated identity, invalidates the HTTP session, and revokes a matching supplied device token when present.
- `updateProgress(email,xp,level,deviceToken)`: requires the same authenticated identity and a valid trusted-device token; validates XP in `[0,999]` and level in `[1,1000]`; updates and saves those values for the user.
- `forgotPassword(email)`: rejects malformed email; uses the same success text for unknown and known users to reduce account enumeration; for a found user stores a recovery OTP and attempts email delivery, removing the challenge if delivery fails.
- `resetPassword(email,otp,newPassword)`: validates email and password length before consuming the recovery code; requires a six-digit valid code and existing user; hashes/saves the new password and revokes the device token.
- `getClassroomStudents(code,authentication)`: requires teacher/admin role, validates the classroom code and resolves the persisted class; only the owning teacher or an admin receives student email, name, role, XP, and level.

Implementation boundary: OTP challenges and device tokens are process-local maps, so they do not persist across restarts or coordinate across multiple instances. This is a description of current behavior, not a claim that the storage design is production distributed-session storage.

#### `ClassroomController` — `controller/ClassroomController.java`

- Constructor stores `ClassroomRepository`.
- `createClassroom(name,teacherEmail)`: creates a `ClassroomEntity`, sets name and teacher, generates a six-character uppercase prefix from a UUID, saves, and returns it. The controller coordinates persistence and code creation.
- `getTeacherClassrooms(email)`: queries by teacher email and returns the list in an OK response.

#### `ClassroomWsController` — `controller/ClassroomWsController.java`

Owns the messaging template and delegates room state/ownership to `RoomSessionService`.
- Constructor stores the broker and shared room-session service.
- `setTopic(SetTopicMessage,Authentication)`: accepts only a teacher identity; delegates topic bounds and room-owner checks; privately sends `TOPIC_CHANGE` to each joined student and the teacher through `/queue/classroom/{code}`. Unauthorized teacher attempts are rejected; invalid/expired room requests disclose no room data.

Nested `SetTopicMessage` DTO: `getCode`/`getTopic` return the two private fields; `setCode`/`setTopic` populate them for message binding. These ordinary accessors let Spring deserialize STOMP JSON into the message object.

#### `RoomSessionService` — `service/RoomSessionService.java`

Owns process-local concurrent room state and enforces access rules for both REST and STOMP paths.
- `createRoom(teacher)`: validates identity, allocates a collision-free random four-digit active code, and creates a typed room session.
- `joinRoom(code,student)`: validates the identity/code and adds the student idempotently.
- `getStatus(code,requester)`: returns status only to the teacher or a joined student.
- `setTopic(code,topic,requester)`: permits only the owning teacher and bounds/normalizes the topic.
- `isMember(code,identity)` and `getStudentsForTeacher(code,requester)`: expose narrow membership checks/member snapshots for the WebSocket authorization and delivery boundary.
- `RoomView(code,topic,studentCount)`: immutable public DTO; deliberately omits teacher and student identities.

Room records are intentionally ephemeral and process-local; restart persistence, expiry, quotas, and clustering remain outside this implementation.

#### `ClassroomChannelInterceptor` — `config/ClassroomChannelInterceptor.java`

- `preSend(message,channel)`: requires an authenticated principal for STOMP CONNECT/SEND and allows subscriptions only to `/user/queue/classroom/{four-digit-code}` when the authenticated identity is a room member. Other destinations and unauthenticated/outside-room subscriptions are rejected.
- `authenticatedIdentity(accessor)`: obtains the connection's server-provided principal and rejects missing/unauthenticated principals; client payloads do not set the identity.

#### `RoomController` — `controller/RoomController.java`

- Constructor stores the shared `RoomSessionService`.
- `createRoom(teacher)`, `joinRoom(code,student)`, `setTopic(code,topic,authentication)`, and `getStatus(code,authentication)`: map REST endpoints `/api/room/*` and legacy `/api/multiplayer/*` to the shared service. #### `PhishingController` — `controller/PhishingController.java`

- Constructor stores `PhishingAnalyzer`.
- `analyze(UrlRequest)`: rejects null/blank URL with HTTP 400; otherwise delegates analysis and returns the resulting `PhishingReport` with HTTP 200.
- `UrlRequest` record: wraps the URL string supplied in JSON; accessor generated.

#### `PlayerProfileController` — `controller/PlayerProfileController.java`

- Constructor stores `PlayerProfileRepository` and `TOTPService`.
- `getAllPlayers()`: loads all entities, maps each through `PlayerView.from`, and returns only safe public DTOs.
- `createPlayer(PlayerCreateRequest)`: rejects null, empty, or over-80-character usernames; trims it; creates a profile only for the authenticated username; generates and assigns a TOTP secret server-side; saves; returns `PlayerView` rather than the entity/secret.
- `getPlayer(id,authentication)`: fetches by ID, returns a safe DTO only to that player or teacher/admin, denies another player's request, or returns 404 if absent.
- `updateScore(id,delta)`: teacher-only; bounds delta to ±10,000 and the resulting score to 0–1,000,000, then saves and returns the safe DTO; returns 400/404 for invalid/missing targets.
- `deletePlayer(id)`: checks existence, returns 404 if missing, otherwise deletes and returns 204.
- `PlayerCreateRequest` record: accepts only username, preventing caller-provided score/badge/TOTP values from binding into the entity.
- `PlayerView` record: response fields are id, username, score, badge count, and creation time. Static `from(PlayerProfile)` copies exactly those public fields and omits the secret. Record accessors are compiler-generated.

- `getEventsByScenario(scenarioId)`: retrieves scenario logs oldest first.

- `getAllCoachFeedback()`: returns all feedback rows.
- `createCoachFeedback(feedback)`: saves and returns the submitted feedback entity.
- `deleteCoachFeedback(id)`: checks existence and returns 404 or deletes and returns 204.

### 4.6 Phishing analyzer

#### `PhishingAnalyzer` — `phishing/PhishingAnalyzer.java`

- `analyze(rawUrl)`: trims input; extracts host/path/query; independently applies ten heuristics (HTTP, IP host, long domain, punycode, suspicious TLD, spoofed brand string, excessive hyphens, deep path, excessive host dots, and long query); adds their configured contributions; clamps score at 1; maps to a band; and returns a report with the original URL and indicator list. It exists as a local rule-based classifier and explanation source.
- `extractHost(url)`: parses with `URI.create` and returns host; catches parse exceptions and returns null so malformed URI portions do not abort the remaining heuristics.
- `extractPath(url)`: same guarded parsing pattern for path.
- `extractQuery(url)`: same guarded parsing pattern for query.
- `toBand(score)`: returns `SAFE` below `.25`, `SUSPICIOUS` below `.55`, otherwise `DANGEROUS`.

Nested `PhishingReport` record stores URL, score, band, and triggered indicators; standard accessors are generated. `isDangerous()` compares band to `DANGEROUS`; `isSafe()` compares it to `SAFE`. These named predicates save callers from repeating string comparisons.

### 4.8 Risk subsystem

#### `RiskFeature` — `risk/RiskFeature.java` (record)

Components are password entropy, geo distance, time deviation, UA similarity, failure streak, MFA type, and training label. Canonical constructor/accessors are generated.
- Convenience constructor without label: delegates with label `-1` to mark inference-only data.
- `toVector()`: transforms inputs into six risk-oriented values in `[0,1]`: weak password, distant location, unusual time, dissimilar UA, repeated failures, and weaker/no MFA all increase the vector. Each component is normalized/inverted as needed and passed through `clamp`.
- `clamp(value)`: private static helper; converts NaN to 1 and otherwise bounds to `[0,1]`. This keeps invalid/non-finite numeric values from propagating NaN through downstream scores.

#### `RuleBasedLayer` and nested `RuleScore` — `risk/RuleBasedLayer.java`

- Constructor: stores `ModelWeightRepository` used for adjustable weights.
- `score(RiskFeature)`: gets normalized vector and weights; computes each weight×feature contribution and total weighted mean; clamps total and returns `RuleScore` including contributions and feature-name array.
- `loadWeights()`: fetches rows ordered by index; if any of the six expected feature rows are absent, returns all defaults; otherwise fills a six-slot array from valid indices using finite absolute values (importance magnitude rather than signed LR direction).
- `RuleScore` record stores total and per-feature data; component accessors generated.
- `topFeature()`: scans contribution values and returns the name at the largest index.
- `topKIndices(k)`: sorts feature indices by contribution descending and copies up to `min(k,featureCount)` indices into a primitive array.
- `band()`: categorizes the contained score using `<.3 LOW`, `<.6 MEDIUM`, else `HIGH`.

#### `LogisticRegressionModel` — `risk/LogisticRegressionModel.java`

- Constructor stores `ModelWeightRepository`.
- `predict(RiskFeature)`: obtains risk vector, loads feature weights and bias, computes bias plus dot product, and applies sigmoid to produce a probability.
- `sigmoid(z)`: computes `1 / (1 + exp(-z))`, mapping the real-valued logit to a probability.
- `loadWeights()`: if there are no rows returns default weights; otherwise builds a feature-sized array from rows with valid indices. (Missing individual indexed rows in a non-empty table retain zero in this method’s initialized array.)
- `loadBias()`: queries the `bias` feature name and falls back to default bias.
- `train(samples,epochs,learnRate)`: starts from default weights/bias; for each epoch, loops samples, computes predicted probability and error against label, accumulates weight/bias gradients, divides by sample count and applies gradient-descent updates; finally persists the trained coefficients. Training depends on samples having labels.
- `persistWeights(weights,bias)`: for each feature name, finds or creates the DB row, updates and saves its weight; then does the same for the bias row.
- `dot(a,b)`: computes the element-wise product sum used by prediction/training.

#### `RiskEngine` and nested `RiskAssessment` — `risk/RiskEngine.java`

- Constructor stores rule layer, LR model, and feedback generator.
- `evaluate(RiskFeature)`: gets rule score and LR prediction; blends 60% rule/40% LR; clamps final score; derives severity; gets the three leading rule contributions and names; requests matching tips; and returns all final/component values.
- `toBand(score)`: maps score `<.3` to `LOW`, `<.6` to `MEDIUM`, otherwise `HIGH`.
- `RiskAssessment` record packages score, band, factors, tips, and component scores. Accessors are generated; no extra custom methods are declared.

#### `CoachFeedbackGenerator` — `risk/CoachFeedbackGenerator.java`

- Constructor stores `CoachFeedbackRepository`.
- `generate(topFactorNames,severityBand,k)`: visits up to `k` factor names in provided importance order; queries exact factor+severity; appends the first exact tip when available; otherwise queries any tip for that factor and appends its first match; returns the resulting list. This turns numeric explanations into human-facing learning feedback.

#### `SyntheticDataGenerator` — `risk/SyntheticDataGenerator.java`

- `generate(count,seed)`: constructs seeded `Random`, repeats `count` times, selects anomaly with probability `.45`, calls the matching private sample builder, and returns the labeled list. Seeded randomness makes identical arguments reproducible.
- `generateLegitSample(Random)`: samples strong entropy, near geography, familiar time/UA, low failures, MFA, and label 0.
- `generateAnomalousSample(Random)`: samples weaker entropy, large geographic/time deviations, unfamiliar UA, more failures, weaker MFA, and label 1.
- `toCsv(samples)`: starts with `CSV_HEADER`, appends each feature in matching column order with formatted decimal fields, and returns text for export/inspection.

### 4.9 Services

#### `EmailService` — `service/EmailService.java`

- Constructor stores `JavaMailSender`.
- `sendOtpEmail(to,otp)`: constructs a `SimpleMailMessage` with sender, recipient, subject, and five-minute OTP text; sends it; returns true on success. On exception, logs only exception type (not the OTP) and returns false so authentication can fail closed.

#### `LeaderboardService` — `service/LeaderboardService.java`

- Constructor stores leaderboard and scenario repositories.
- `recordResult(username,scenarioId,outcome,entropyScore,riskScore)`: loads scenario or throws; chooses base points (SUCCESS 1000, PARTIAL 500, otherwise 100); computes `entropyScore * 200 / 100.0` and `riskScore * 300` (the documented inputs are 0–100 and 0.0–1.0, but the method does not clamp either input); floors the total at zero; finds or creates the unique player/scenario entry; changes stored data only if new score beats personal best; saves; calls rerank; returns entry.
- `rerank(scenarioId)`: fetches all scenario entries sorted descending by score, writes ranks starting at 1, then saves them together.
- `getTop10(scenarioId)`: delegates to ordered top-ten repository query.
- `getPlayerHistory(username)`: delegates to the player’s score-descending query.

#### `ScenarioGeneratorService` — `service/ScenarioGeneratorService.java`

Curated static question banks are data, not classes or methods.
- `generateScenario(topic,type)`: dispatches `crypto`, `phishing`, and `matching` to their builders; unknown type falls back to crypto. The JSON contract keeps the existing frontend parsers independent of how questions are selected.
- `buildCryptoJson(topic)`: chooses the topic’s bank (fallback `crypto`), shuffles that list, selects up to three questions, escapes string fields, and writes the `q/opts/ans/expl` JSON array. In the current code the selected bank itself is shuffled in place.
- `buildPhishingJson()`: copies the default URL bank before shuffling, selects up to six rows, escapes URL/reason, and builds JSON records.
- `buildMatchingJson()`: chooses one default term/definition row and serializes its three terms and three definitions.
- `escape(String)`: escapes backslashes and quotation marks for the JSON strings assembled by these builders.

#### `SimulationEngine` — `service/SimulationEngine.java`

Nested `SessionState` enum: `INIT`, `AUTH_ATTEMPT`, `MFA_CHALLENGE`, `SUCCESS`, `LOCKED`, `DENIED` are the finite states returned to callers.
- Constructor stores scenario/event repositories and TOTP service.
- `processLoginAttempt(scenarioId,username,password,failedAttempts)`: loads scenario or throws; checks lockout first and logs/returns `LOCKED`; calculates Shannon entropy and maps it to score; logs/returns `DENIED` if below scenario threshold; if MFA is required logs and returns a successful-but-challenged result; otherwise logs and returns `SUCCESS`. Each path builds a `LoginResult`. The implementation is a direct synchronous sequence of branches.
- `processTOTPVerification(scenarioId,username,totpSecret,code,failedAttempts)`: loads scenario; returns/logs lockout when failures meet threshold; asks `TOTPService` to validate the code; logs success or failure and returns `SUCCESS` or another MFA challenge.
- `calculateShannonEntropy(input)`: returns 0 for null/empty; counts each character; sums `-p*log2(p)` across observed characters. This estimates character-distribution entropy for the simulation policy.
- `entropyToScore(entropy)`: linearly scales 0–5 bits to 0–100, capped at 100, and converts to integer.
- `log(...)`: creates an `EventLog` and saves it through the event repository.

Nested `LoginResult` class: constructor sets the four public final fields `success`, `message`, `nextState`, and `requiresMfa`; no accessor methods are declared. It is the result value shared between engine and controller.

#### `TOTPService` — `service/TOTPService.java`

- Constructor initializes a default secret generator and a SHA-1 code generator/verifier using system time.
- `generateSecret()`: delegates secret creation to the library generator.
- `verifyCode(secret,code)`: delegates validation to the configured verifier and returns its boolean.

### 5.2 `MiniGames` object — `minigames.js`

`MiniGames` is an object literal containing state and function-valued properties; it is not declared with `class`. Its `start...` methods accept difficulty and win/loss callbacks, show a briefing (the incident-command round presents its briefing in the game panel), and render into either the arcade container or campaign target. Their local timers/listeners/callbacks are implementation details rather than separate class methods.

- `trackInterval(callback,delay)`: starts an interval, stores its ID for cleanup, and returns it.
- `trackTimeout(callback,delay)`: starts a timeout that removes its own ID from the tracked list before calling the callback; returns ID.
- `cleanup(clearContent=true)`: clears tracked timers, resets timer state, removes briefing overlay, and optionally empties the current target container.
- `showBriefing(title,text,onStart)`: constructs a mission overlay, inserts briefing and start button, and removes overlay/calls callback on start.
- `startFirewall(difficulty,onWin,onLose)`: spawns falling safe/malicious packets at difficulty-scaled speed/rate; click/ignore outcomes affect health/score; when traffic ends or health is depleted it calls the appropriate callback.
- `startSQLi(...)`: selects a difficulty-specific query and payload options, shuffles them, renders choices, then compares selected payload after a short tracked timeout and calls win/loss.
- `startRansomware(...)`: creates a difficulty-scaled grid with one infected node; users can take clean nodes offline; interval-based neighbor spread updates infection count and ends with win if contained or loss if network fully infected.
- `startPrivEsc(...)`: creates a small node/access/inventory scenario; difficulty changes where items reside; nested `renderMap` redraws access state; clicking current node collects its item or wins at `Win`, clicking accessible node moves, locked node warns and shakes panel.
- `startCryptoDecoder(...)`: encodes a target word with difficulty-specific Caesar shift, renders shift controls, updates decoded preview as shift changes, and compares submitted preview to target for win/loss.
- `startRBAC(...)`: creates role/badge requirements and shuffled draggable badges; event handlers validate drops, mark correct assignments, call win after all match, or show least-privilege breach feedback and call loss for mismatch.
- `startPhishingSwipe(...)`: shuffles URL examples and selects difficulty-specific count; renders draggable card plus button fallbacks; nested answer/drag handlers interpret right as safe and left as phishing; wrong answer calls loss, all correct cards call win.
- `startWhackAMole(...)`: spawns malicious and legitimate popups; clicking malicious increments target score, clicking legitimate reduces health, and unhandled malicious popups damage health after timeout; stops and calls win/loss at thresholds.
- `startIncidentCommand(...)`: runs three timed branching incident decisions. It tracks containment, uptime, evidence, attacker pressure, and combo; each choice or timeout updates the state and debrief; final state produces a grade/XP/summary and offers completion/replay. This is a branching teaching simulation, not merely a multiple-choice quiz.
